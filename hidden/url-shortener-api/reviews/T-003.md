## Findings

**RV-001 — advisory — target: architect**
`spec_ids: ["url-shortener-api:BEH-003", "url-shortener-api:CTR-001", "url-shortener-api:BEH-004"]`

Record quote (`url-shortener-api:BEH-003`, `when`/`then`): a POST /links body "lacking url, or with the url key present but its value empty, not a string, relative, or carrying a scheme other than http and https" answers "400 with JSON error equal to invalid_url"; `url-shortener-api:CTR-001` `error_taxonomy` likewise lists `400 invalid_url (missing, relative or non-http/https url)` separately from `400 invalid_json (body is not JSON)`.
Diff: `src/routes/links/index.ts:34-37` answers `invalid_url` for the missing-key and non-string cases, and `index.ts:30-33` answers `invalid_json` only when `JSON.parse` fails — the implementation matches the records. The design/tech.md M-03 sentence, however, says the route "Raises `invalid_json` for a body that does not parse or does not hold a `url` key of string type", which read literally would answer `invalid_json` for a missing or non-string `url` and so contradict BEH-003. The conflict sits in the design prose only: the M-03 signature, entry path, dependencies and return contract all match the implementation, and no record is left unrealised, so the finding is advisory and the paragraph should be corrected on the next architect pass.

No blocking findings.

All twelve covered records carry a `@covers` marker in the frozen test file and an asserting test that survives the flip test on its `then`, `postconditions`, `error_taxonomy` or policy predicate; none is vacuous. Verifier evidence is green with `testsUnchanged: true` and `writeSetOk: true`, so `decision: advisory_only`, `target: none`.

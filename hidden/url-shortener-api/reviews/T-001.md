## Findings

**RV-001 — advisory — architect — `url-shortener-api:POL-001`, `url-shortener-api:INV-003`**

Evidence: `url-shortener-api:INV-003.statement` requires the code value to be "taken from the error taxonomy of the responding contract", and `url-shortener-api:CTR-006.error_taxonomy` names the invalid-port condition only as `exit invalid_port` (a non-zero process exit), never as an HTTP status; `src/errors/index.ts:19`: `ERROR_STATUS` assigns `invalid_port: 0`.

`ERROR_STATUS` is declared as a total `Readonly<Record<ErrorCode, number>>` in the M-01 interface, so the implementer had to supply a number for a code that no contract ever answers over HTTP. Status `0` is not a valid HTTP status and is not named by any record; a caller that routed `errorResponse("invalid_port")` through a server would emit a status no contract's taxonomy names (and a status Node would reject). The behaviour is not reachable in this task — `invalid_port` is consumed through `exitStatus` — so no in-scope record is unrealised, and this is recorded as advice for `design/tech.md`: either narrow the `ERROR_STATUS` key type to the HTTP-answerable codes or state in the interface section that `invalid_port` has no HTTP status. No change is demanded of the implementer or the test-writer.

## Findings

### RV-001 — advisory — target implementer — expense-ledger-cli:CTR-006, expense-ledger-cli:BEH-015

`expense-ledger-cli:CTR-006.schema.stdout` fixes the usage text as "usage text naming the add, list, summary, rm and export commands and the --help option", and `design/tech.md` section 5.2 states each `USAGE_TEXT` line carries "its argument shape as written in CTR-001 to CTR-006". `src/parse/index.ts:16` writes `[--note text]` where CTR-001 writes `[--note <text>]`, and `:17` writes `[--category name]` where CTR-002 writes `[--category <category>]`; `:19` writes `export --csv` where CTR-005's command line is `ledger export --csv`. The command names, the exit path and the argument vocabulary are all correct, and CTR-006.compatibility_rules makes the text informational, so this does not make any record unprovably realised — it is recorded for trace only, not a rework request.

### RV-002 — advisory — target test-writer — expense-ledger-cli:BEH-002

`expense-ledger-cli:BEH-002.then` constrains only "exit 2, one line on stderr starting with `usage:`, and the ledger still holds N expenses"; nothing in the record or in the M-04 interface (`date?: string`) requires the `date` key to be present on a successful parse without `--date`. `tests/parse/parse.test.ts:33-36` nevertheless evaluates `"date" in result.command ? result.command.date : "absent"` and asserts `toBeUndefined`, so an implementation that omits the key — legal for an optional property and behaviourally identical for every other record — fails the frozen suite. The current implementation satisfies it (`src/parse/index.ts:114` writes `date` unconditionally), so the suite is green; the note is that the test freezes an incidental shape rather than the record's obligation. Advisory because no record is contradicted.

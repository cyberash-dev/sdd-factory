## Verdict rationale

All ten ids carry a `// @covers` marker in the frozen test file (`tests/rooms/rooms.test.ts` lines 9, 26, 52, 80, 97, 107, 125, 147, 161, 175) and each has at least one test that asserts the record's own text, so rule 1 is met. The flip test was applied per id: inverting the expectation would break the asserting test in every case — e.g. a non-persisting `createRoom` breaks BEH-001's third assertion (line 14), an accepting validator breaks the `invalid_room` assertions of BEH-002/BEH-003 (lines 27-44, 53-70), a case-sensitive duplicate check breaks BEH-004 (line 81) and INV-005 (line 98), a lexicographic or absent sort breaks BEH-005 (line 130) where `r10` must follow `r9`, a wrong filter or bound breaks BEH-006/CTR-002 (lines 148-158, 176-188), and a lenient `minCapacity` parser breaks BEH-007 (line 162). No test is vacuous.

Predicates (`rule 2`) hold for every input class the records name, including every `negative_cases` entry, and the codes emitted come from `CTR-010`'s taxonomy with statuses supplied by the already-green `statusOf` mapping. Mechanics (`rule 3`) are settled by `testsUnchanged: true` and `writeSetOk: true`. Local semantic risk (`rule 4`) is absent: the module is pure in-memory logic with no promises, timers or handles; the error paths return documented codes instead of throwing; ordering is deterministic numeric sort; and work is a linear scan or a bounded `n log n` sort over an in-memory array. No behaviour beyond the spec (`rule 5`): the only extra branches are "non-object body → `invalid_room`", "unknown body property ignored" and "unknown query parameter ignored", each of which is either a documented code under POL-002 or the exact wording of the M-03 interface text and ASM-006. No record was found too vague to assert, no missing negative case was implied but unnamed, and no two records conflict, so no `contract` finding (`rule 6`). No interface drift (`rule 7`).

choices:
- "Module boundary vs HTTP boundary." Several covered records phrase their `then` in HTTP terms (201, `Content-Type`, 404 `not_found`, 405 `method_not_allowed`, 400 `invalid_json`). `design/tech.md` puts those concerns in M-02 and CTR-010, and T-002's routing tests are green in the verifier evidence, so I judged conformance at the M-03 boundary (returned value plus error code) rather than demanding HTTP-level assertions from `tests/rooms/**`. This is not a gap: every HTTP clause of the covered records has an owner elsewhere in the task graph and an existing green test.
- "Defensive non-object branch." `createRoom(null | "x")` returning `invalid_room` (`src/rooms/index.ts:24`) is not named by a record, but it emits a documented error code for a body that fails validation, which POL-002 and the M-03 text both cover; I did not treat it as behaviour beyond the spec.

Both tests assert something real (the empty-state path and the parameterised BEH-007 matrix), the duplication is a naming/reporting ergonomics matter only, and rule 12 forbids blocking on style, so I logged it here instead of raising a finding.

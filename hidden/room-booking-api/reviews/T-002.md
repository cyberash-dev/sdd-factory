## Verdict rationale

Every one of the seven records has a `// @covers` marker in the frozen test file and at least one non-vacuous test: for each ID the flip test finds an assertion that fails if the record's expectation were inverted. Predicates hold in `src/rooms/index.ts` for every input class the records name, including all `negative_cases`: the name must be a string, non-blank and at most 40 code points (`:10`-`:16`, matching `CTR-001.schema.request_body` and ASM-003/ASM-004); capacity must be an integer in `1..100` (`:18`-`:25`); the duplicate check lower-cases through `RoomStore.findByNameIgnoringCase` and runs after field validation, so `BEH-003`'s valid-name case returns `room_name_taken` while `BEH-002`'s empty-name case still returns `invalid_room` (`:33`-`:38`); the room is stored exactly as submitted, untrimmed, with no client-supplied `id` (`:39` reads only `name` and `capacity`); `listRooms` returns `{rooms}` in store order, rejects a present `minCapacity` that is not a decimal integer (`/^\d+$/`, so `-1`, `1.5` and `abc` fail the pattern and `0` fails the `< 1` guard) with `invalid_query`, and filters inclusively with `capacity >= minCapacity` (`:42`-`:55`). Error codes come from the shared catalogue, whose statuses (400 `invalid_room`/`invalid_query`, 409 `room_name_taken`) are asserted green in this same run by `tests/errors/errors.test.ts`. The implementation adds nothing no record names — no extra field, flag, route or output shape — and the module path and signatures are exactly `design/tech.md` `M-04`, so there is no interface drift. Local semantic risk is absent: the module is synchronous, holds no timer, socket or file handle, has no error path that could yield a wrong exit code or status, and does bounded work over the in-memory room list; `concurrency_model.idempotency` is `none` for the write records and `read_only` for the listing records, so no nondeterminism concern applies. Mechanics are settled by evidence (`testsUnchanged: true`, `writeSetOk: true`, typecheck exit 0, 71/71 tests green), not by inspection.

choices:
- `BEH-002`/`BEH-003` name a status (400 / 409) while the `M-04` failure variant carries only a code; the status is derived by `STATUS_BY_CODE` in `src/errors/index.ts` and asserted there by T-001's catalogue tests, green in this run. I treat "code asserted at the module boundary, status proved by the shared catalogue" as satisfying the records rather than as a coverage gap, and raise no finding.
- `BEH-001.negative_cases` also names "body not valid JSON => 400 invalid_json". `M-04` receives an already-parsed `body: unknown`, so JSON syntax is not expressible at this interface; `design/tech.md` assigns it to the composition layer and `BEH-018`/`CTR-007` in T-006 carry it. Likewise the `404 not_found` and `405 method_not_allowed` entries of `CTR-001`/`CTR-002` and the `Content-Type` clause of `BEH-001`/`BEH-004` are routing and envelope obligations of `INV-002`/`BEH-019` in T-006. Not gaps for T-002, so no finding against the records.
- `BEH-004`'s "ordered by id" cannot be distinguished from creation order here because rooms are never deleted and ids are a monotonic counter (OQ-001/OQ-002 defaults), so the three-room assertion is still non-vacuous (a descending or shuffled order fails) even though both correct orderings coincide.

No record obliges an array-body case and the array guard at `src/rooms/index.ts:28` is not required by any record, so this is test hygiene with no spec consequence; it is logged here instead of as a finding.

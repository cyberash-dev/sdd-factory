## Findings

**RV-001 — advisory, target contract.** `room-booking-api:BEH-006` and `room-booking-api:CTR-004` fix the echoed body as the submitted title; `spec.md` `room-booking-api:OQ-001` describes the default only as "trim before validation, so a whitespace-only value is invalid", and `ASM-001` repeats the validation scope. `src/booking-writes/index.ts:40` returns `{ title: trimmed, ... }`, so `"  Standup  "` is stored and echoed as `"Standup"` (asserted at `tests/booking-writes/booking-writes.test.ts:81`). No record says the stored title is trimmed. This is not a rule-5 "behaviour beyond the spec" (no new field, format or route), it is the natural reading of the OQ-001 default, and no record is contradicted — but the spec should state whether the stored/echoed title is trimmed, so this goes to trace for the contract owner. No rework needed; the tests would have to change only if the spec later says the raw title is stored.

**RV-002 — advisory, target none.** `room-booking-api:BEH-008` requires that a start without the `Z` suffix, with seconds, or with milliseconds is `invalid_booking`, and `src/booking-writes/index.ts:9` implements a strict local form (`:09:00Z`) to do so, correctly. The exported `parseTime` in `src/domain/index.ts` accepts a seconds-less `YYYY-MM-DDTHH:MMZ` instead, so the codebase now carries two time parsers with different acceptance sets; a later module (query windows, availability) reaching for the domain helper would accept a spelling BEH-008 rejects. Nothing in this task is wrong today, hence advisory-only, but the divergence is the kind of local semantic risk worth a trace note.

**RV-003 — advisory, target contract.** `room-booking-api:BEH-006` says the server "holds M bookings across all rooms" and the new id is `b<M+1>`, which, read as the held count, would reuse `b2` for the rebooking in `room-booking-api:SCN-002` after `b1` is deleted, while SCN-002 requires `b3`. The pair is consistent only under the `spec.md` Glossary ("b1, b2, ... in creation order across all rooms") and `INV-002` ("a deleted id is never reused"), i.e. when `M` counts bookings created, not bookings currently held. `src/booking-writes/index.ts:60` assigns through `addBooking`, whose `bookingSeq` is creation-based and never recomputed (`src/domain/index.ts`), matching SCN-002, and `tests/booking-writes/booking-writes.test.ts:328` asserts `b3`. The implementation is right and the tests follow SCN-002; the loose wording of BEH-006's `given` is the trace item, so it is routed to contract rather than to the implementer. Advisory, because both records hold under the Glossary reading.

No blocking findings. There is no coverage gap (all twelve markers present, every test non-vacuous under the flip test), no missing predicate for a named input class, no error-taxonomy mismatch, no `testsUnchanged`/`writeSetOk` problem (both `true` in `verifier.json`), and no interface drift from M-04.

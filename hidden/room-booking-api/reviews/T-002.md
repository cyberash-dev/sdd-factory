## Findings

### RV-001 — `design/tech.md` M-02 states a processing order the implementation does not follow (advisory, target architect)

- Record: `room-booking-api:BEH-022.test_obligation.predicate` — "an unmatched path yields 404 not_found for every method", with negative case `POST /rooms/r1/bookings/x => 404 not_found`.
- Design: M-02 says "The router parses the request line first: for a `POST` it reads the whole body as UTF-8 and runs `JSON.parse`, answering 400 `invalid_json` when the body is empty or not JSON; other methods ignore the body. It then matches the path on segment count and literal segments".
- Code: `src/http/index.ts:96-108` matches the path and method first and returns 404/405 without touching the body; the body is read only at `:116`, after a route is selected.
- Why it matters and why it is not blocking: for every input the records name, both orders agree — a `POST` to a documented body route with an unparseable body is 400 `invalid_json` either way (`BEH-021`), and an unmatched path is 404 either way for requests whose body parses (`BEH-022`'s cases). The orders diverge only for a `POST` to a path that matches no route *with an empty or malformed body*: the design text would answer 400 `invalid_json`, the implementation answers 404 `not_found`. `BEH-022`'s predicate ("for every method", no exception for a bad body) and its `POST /rooms/r1/bookings/x => 404` negative case read in favour of the implementation, so nothing in the record set is unrealised. The ambiguity is in the design text: if M-02's order were taken literally, a `POST` to an unmatched path with an empty body could not satisfy `BEH-022`, and a later implementer reading M-02 could build a router that fails `BEH-022` on that input. Routing this to `architect` (one clarifying sentence: "match the path first; read the body only once a route is selected") removes the trap. It is advisory because the current diff satisfies the records.

### RV-002 — a throwing route handler leaves a `POST` unanswered while the same fault escapes on other methods (advisory, target implementer)

- Record: `room-booking-api:POL-002.predicate` — "a missing, mistyped, malformed or out-of-range input is answered with the documented 400 or 422 status and the process keeps serving subsequent requests", with negative obligation "a request after a rejected one that receives no answer fails the check".
- Code: `src/http/index.ts:79` calls `route.handle` with no guard. On the `POST` path it runs inside the promise created at `:116`, which is consumed with `void`, so a throw rejects a promise nobody handles: the request is never answered and, on current Node, the rejection is reported out of band. On the `GET`/`DELETE` path the same throw propagates out of the request listener (an uncaught exception), so the two methods fail differently for the same handler fault.
- Why it is advisory and not blocking: no record names a *handler fault* as an input class — `POL-002` is about request bodies and query strings, and every malformed or out-of-range input is answered from the router's own parse step (`:116-121`) or by the injected handler returning `kind: "error"` without throwing, which is what the tests exercise. M-02 also states deliberately that "The router adds no catch-all status: no error code exists for an internal fault (DD-13)", so inventing a 500 or a catch-all is not available to the implementer. The note is that the two paths should degrade the same way (both answering nothing, or both surfacing the fault) rather than one hanging a request silently; if the design intends the fault to surface, the `void readBody(...).then(...)` form hides it.

Behaviour matches the record text rather than the tests: 404 comes only from a path mismatch, 405 only from a path match without a method match, 400 `invalid_json` only from a failed `JSON.parse` before the handler runs, error statuses come from `statusOf` in `src/core/index.ts` (so the envelope and codes are the `CTR-010` ones), and 204 is written with no body and no content type. No flag, endpoint, field or format that no record names was added — the injected route table and the `:name` capture are the M-02 interface. The two findings are advisory: one is a design-text trap that the current code sidesteps in the record-conformant direction, the other is a fault-path asymmetry that no record's input classes can reach, and M-02 explicitly forbids the catch-all that would "fix" it. Hence `advisory_only`; the task is approved and both notes go to trace.

## Findings

### RV-001 — advisory — target: none

`spec_ids`: `room-booking-api:CTR-004`

Evidence: `room-booking-api:CTR-004.error_taxonomy` lists `404 not_found - unknown route` and `405 method_not_allowed - method not supported on this route`; `tests/booking-list/booking-list.test.ts:166-178` asserts only `400 invalid_query` and `404 room_not_found`, and `src/booking-list/index.ts:24` exposes the pure `HandlerResult` function `listBookings` that cannot express a route fallback.

Detail: the two unasserted taxonomy entries are routing concerns that M-06's interface deliberately does not model — the module hands back a `HandlerResult` and the router owns unknown paths and unsupported methods (`CTR-007`, another module and task). Nothing inside this task's write-set (`src/booking-list/**`, `tests/booking-list/**`) can observe them without an HTTP server harness, so no rework is requested and the finding is recorded for the trace so the deferral to the router contract is visible. They are not counted as a missing behaviour in this diff.

### RV-002 — advisory — target: none

`spec_ids`: `room-booking-api:BEH-012`

Evidence: `room-booking-api:BEH-012.test_obligation.boundary_classes` names `booking fully inside`; `tests/booking-list/booking-list.test.ts:93` labels the 13:15Z-13:45Z filter `booking fully inside` although it asserts a booking containing the filter, and the fully-inside case is only exercised at `tests/booking-list/booking-list.test.ts:171` under the CTR-004 marker.

Detail: the assertions themselves are correct against the record (`b3` 13:00Z-14:00Z does overlap 13:15Z-13:45Z, so `["b3"]` is right, and `08:00Z-12:00Z` keeping `["b1","b2"]` is the genuinely contained case), so no behaviour is left unproven. Only the case label misdescribes what it exercises, which is a naming defect, hence advisory.

## Verdict rationale

All five required records have a `// @covers` marker in `tests/booking-list/booking-list.test.ts` and at least one non-vacuous asserting test: for each record I asked whether inverting the record's expectation would fail a test, and it would (unordered list, descending id tie-break, boundary treated as overlap, one-sided filter treated as unbounded, empty array for an unknown room, filter ignored). Every `negative_cases` entry of `BEH-011`, `BEH-012`, `BEH-013` and `BEH-020` has a matching case, and the implementation emits exactly the codes and statuses of `CTR-004.error_taxonomy` at the handler level. The diff contains no endpoint, field, flag or format outside the records, no mutation of store state on a read-only path, no unhandled rejection and no unbounded work. Verifier evidence settles the mechanics (`testsUnchanged`, `writeSetOk`, typecheck 0, 72/72 green). The two advisory notes are trace material, not requests for change, so the task is approved.

choices:

- Failure results carry no HTTP status (`ApiFailure` has `code` only), and the records' `then` clauses speak in statuses ("404", "400"). I judged the code assertions in the tests plus `statusForCode` (`invalid_query` ⇒ 400, `room_not_found` ⇒ 404, asserted in `tests/errors/errors.test.ts`) as satisfying the record at the module boundary M-06 defines, rather than demanding an HTTP harness the interface does not provide.
- `BEH-011`'s `then` instantiates `b3` at 09:00Z-11:00Z so that `[b2, b1, b3]` exercises the id tie-break; the test file instantiates `b3` at 10:00Z-11:00Z in the order test and covers the tie-break in a separate equal-start test. I judged the record covered by the pair, since the record asserts ordering semantics rather than one literal fixture.
- "Equal starts ordered by creation time" (`BEH-011.test_obligation.failure_scenarios`) is not distinguishable from id order in this product, because `createStore` assigns ids in creation order and never reuses them. No test (and no reviewer) can separate the two; I therefore did not treat that as a coverage gap or a test-writer defect.
- A stored booking whose times do not parse is dropped from a filtered listing (`src/booking-list/index.ts:51-52`) while still appearing unfiltered. Such a booking cannot arise through the validated create path (`BEH-007`), and an interval that cannot be parsed intersects nothing, so I treated this as inert rather than as behaviour beyond the spec.
- Unknown-room precedence over an invalid query (`src/booking-list/index.ts:25-33`) is fixed by neither `BEH-012`, `BEH-020` nor `CTR-004`. Since no record states it and no test asserts the contested combination with an invalid filter, I made no finding.

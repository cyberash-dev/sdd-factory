## Findings

### RV-001 — advisory, target `contract`

- `spec_ids`: room-booking-api:BEH-012, room-booking-api:INV-002
- `evidence`: room-booking-api:BEH-012.given: 'the room `r1` has a booking from `2026-11-02T09:00:00Z` to `2026-11-02T10:00:00Z` and a second booking from `2026-11-02T09:30:00Z` to `2026-11-02T11:00:00Z`'; tests/bookings/bookings.test.ts:149-150 stores 09:00-10:00 then 10:00-11:00, because room-booking-api:INV-002 forbids storing the overlapping pair the record's given presumes.
- Detail: BEH-012's `given` cannot be reached through the documented API — INV-002 forbids any two booking intervals of one room from overlapping, so the second booking (09:30-11:00 on top of 09:00-10:00) can never be in the state. The frozen test substitutes the nearest reachable state (a conflict at 09:00 plus an adjacent booking at 10:00) and still asserts exactly what the record's `then` obliges: 409 `room_busy` with `conflictingBookingId` naming the earliest-starting conflicting booking, also when the request spans two bookings (line 157), with the state unchanged. The obligation is therefore realised; what is defective is the record's setup. Restating the `given` (for example a single 09:00-10:00 booking plus the 09:45-10:15 request) would remove the ambiguity for later readers and for any task that reuses BEH-012.

Nothing else deviates. The implementation matches the M-04 signatures and the DD-07 order exactly (room existence → body validation of title, both times, positive duration ≤ 480 minutes and integer attendees ≥ 1 → capacity → conflict), the conflict choice matches DD-11 with the ASM-005 tie-break via `byStartThenId`, and the diff adds no flag, endpoint, field or output format that no record names.

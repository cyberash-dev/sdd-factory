## Spec conformance

- `room-booking-api:BEH-019` — `POST` bodies on both POST routes go through `parseJson`
  (`src/http/server.ts:22-29`) and `asObject`/`withObject` (`src/http/router.ts:25-37`); an
  unparsable, empty, array, string, number, boolean or `null` body yields `invalid_json` (400)
  before any handler runs, so no state changes; the process keeps serving
  (`src/http/server.ts:43-56`). Every `negative_cases` entry holds.
- `room-booking-api:BEH-020` — `matchRoute` returns `not_found` only when no route pattern
  matches the path (`src/http/router.ts:82-88`); the six patterns cover exactly `/rooms`,
  `/rooms/:roomId/bookings`, `/bookings/:bookingId`, `/availability` with no trailing-slash or
  prefix looseness, so `GET /rooms/r1`, `GET /booking` and `DELETE /rooms/r1` are 404 while
  `GET /rooms` is 200. Body is `{"error":"not_found"}` via `errorBody`
  (`src/errors/index.ts:47-52`).
- `room-booking-api:BEH-021` — a path that matches at least one pattern but no route of the
  request method returns `method_not_allowed`, mapped to 405 by `statusFor`
  (`src/errors/index.ts:26-38`); `GET /nope` matches no pattern and stays 404. The unsupported
  method is never dispatched, matching the "not executed" failure scenario.
- `room-booking-api:BEH-022` — `sendJson` is the only writer of a payload response and always
  sets `Content-Type: application/json` (`src/http/server.ts:31-38`); errors go through
  `sendError → sendJson`. The 204 branch writes headers alone with no body and no content type
  (`src/http/server.ts:64-68`). All statuses the record enumerates are covered.
- `room-booking-api:CTR-001` — `resolvePort` reads `PORT`, defaults to 3000, and accepts an
  integer in 1..65535 (`src/index.ts:10-16`); `main` resolves the port and listens
  (`src/index.ts:24-26`), `startServer` resolves on `listening` and rejects on `error`
  (`src/http/server.ts:85-96`). The three taxonomy entries (400 `invalid_json`, 404 `not_found`,
  405 `method_not_allowed`) are the emitted codes on those paths.
- `room-booking-api:INV-005` — the only `Store` is created inside `main` (`src/index.ts:25`) and
  every handler receives it by argument; nothing is written to disk or read back, so a new
  process starts empty.
- `room-booking-api:NFR-001` — build and test are driven by the untouched `build`/`test` scripts
  with `tsconfig.build.json`; typecheck and full suite are 0 by the Verifier evidence.
- `room-booking-api:POL-002` — every rejected input is answered from the `Result` error before
  the handler mutates the store (`src/http/router.ts:35-37`, `src/rooms/index.ts:6-18`,
  `src/booking-writes/index.ts:41-52`), statuses come from the single `STATUS` table, and no
  code path throws on a request-shaped input: `readBody` rejects only on a socket error and
  `createServer` converts that into a torn-down socket, not a crash (`src/http/server.ts:78-84`).

## Verdict rationale

Every one of the fifteen covered records has a `// @covers` marker in the task's own test files,
an asserting test that fails if the record's expectation were inverted, and an implementation
that satisfies the record text for each input class the record names — including every
`negative_cases` entry of BEH-019, BEH-020, BEH-021 and BEH-022 — and the codes and statuses of
CTR-001's `error_taxonomy`. The frozen tests are unchanged and nothing outside `writes` was
touched (Verifier evidence), so the diff provably realises the records and nothing more; with
zero findings the aggregation is `approve`.

choices:

- `room-booking-api:BEH-020` "every path outside the defined endpoint set returns 404": read as
  applying to request targets the URL parser accepts. A target such as `GET //[` makes
  `new URL` throw inside `handle` (`src/http/server.ts:43`), and the `catch` at
  `src/http/server.ts:79-83` destroys the socket instead of answering. No record names a
  malformed request-target, the process survives and no 5xx is produced (POL-002), so this is
  logged rather than treated as a record not realised.
- `room-booking-api:CTR-001` "a PORT value overrides the default port": read as "a PORT value
  that is an integer in 1..65535 overrides it"; a non-numeric or out-of-range value falls back
  to 3000 (`src/index.ts:11-16`), which no record forbids.
- `room-booking-api:BEH-019` with a non-object body on `POST /rooms/:roomId/bookings`: the
  `invalid_json` answer precedes the `room_not_found` check because the body is parsed by the
  router before dispatch (`src/http/router.ts:66-76`). BEH-019 only fixes the body class, and
  the precedence between `invalid_json` and `room_not_found` belongs to ASM-004, which is not
  one of this task's records; no finding.
- Mechanics (`testsUnchanged`, `writeSetOk`) were taken from `verifier.json` as instructed and
  were not re-derived by inspection.

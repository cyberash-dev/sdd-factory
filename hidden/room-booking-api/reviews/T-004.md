## Findings

### RV-001 — BEH-018's worked ordering example contradicts the rule it illustrates (advisory, target: contract)

`room-booking-api:BEH-018.then` says the listing is "ordered b2, b3, b1" for the given where `b1` runs 11:00–12:00 and `b3` runs 11:00–11:30. Both b1 and b3 start at 11:00, so the record's own `negative_cases` entry "two bookings with the same start => ordered by id ascending" — reinforced by `room-booking-api:CTR-004.compatibility_rules` "bookings are ordered by start then by id" and `room-booking-api:INV-007` "GET /rooms/:roomId/bookings returns bookings ordered by start then by id" — requires `b2, b1, b3`. The two expectations in the same record cannot both hold.

The implementation (`src/booking-read/index.ts:41-44`) and the frozen test (`tests/booking-read/booking-read.test.ts:105-111`) follow the rule and therefore assert `b2, b1, b3`, i.e. they realise the record's rule and its negative case and not its worked example. Coverage of the ordering predicate is not harmed (the test would fail on insertion order, on tie-break by end, or on a descending id tie-break), which is why this is advisory rather than blocking: the observable behaviour is determinable from three consistent statements, and only the example instance is mis-derived.

Action implied for the spec-critic: correct the example ordering in `room-booking-api:BEH-018.then` (or restate it as "ordered by start then by id" without a worked instance) so the record is self-consistent. No implementation or test change follows from it.

## Findings

**RV-001 — advisory, target contract.** `room-booking-api:CN-002.test_obligation.predicate: "with PORT set the server listens on that port and with PORT unset on 3000"` can only be observed by binding or probing the default port; `room-booking-api:CN-003.test_obligation.failure_scenarios: ["a test depending on port 3000 being free"]` names that exact arrangement as a failure the suite is meant to avoid. `tests/app/app.test.ts:71-74` honours CN-002 and therefore instantiates the CN-003 failure scenario:

```ts
it("listens on 3000 when PORT is unset", async () => {
  const res = await startedProcessAnswers(3000, { PORT: undefined });
  expect(res.status).toBe(200);
}, 120000);
```

The suite is green in the verifier's environment, but on a host where 3000 is occupied the CN-003 acceptance gate (`npm test` passes) flips on an environmental accident rather than on the product. Both records are individually defensible and cannot both be honoured as written, which is a spec gap for the contract owner — not a request to the test-writer (no other way exists to prove the default) and not to the implementer (the code already defaults correctly at `src/index.ts:3`). Logged for trace; it does not gate this task.

**RV-002 — advisory, target test-writer.** `room-booking-api:CN-001.test_obligation.predicate: "no outbound connection is opened and no third-party runtime dependency is declared"` has two conjuncts; `tests/app/app.test.ts:51-61` asserts the second (the `dependencies` member of `package.json` is empty) plus that `/rooms` is answered locally. The implementation does satisfy it, so this is a coverage note, not a defect; an assertion over the import graph of `src` (only `node:` builtins and sibling modules) would close it. Not blocking: the test is not vacuous for the ID (inverting the dependency conjunct fails it) and the behaviour is provably realised.

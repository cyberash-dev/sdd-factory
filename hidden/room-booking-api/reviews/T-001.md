## Findings

### RV-001 — advisory — target: implementer

- spec_ids: `room-booking-api:INV-007`
- evidence: room-booking-api:INV-007.statement says listings are "ordered by start then by id" and "by capacity ascending then by id"; `src/core/index.ts:74` sorts `bookingsOf` on `startMs` alone and `src/core/index.ts:123` sorts `availableRooms` on capacity alone, so the `then by id` half is produced by ECMAScript stable sort preserving creation order rather than by an explicit id key.

The record is satisfied today: `addBooking` always appends (`src/core/index.ts:102`) and ids come from one monotonic counter (`:93-95`), so creation order is exactly ascending id order, and ES2019 requires `Array.prototype.sort` to be stable. The note is that the invariant is held by an implicit property of the runtime plus an append-only write discipline rather than by the comparator, so any future out-of-order or re-insert write to `bookingList`/`roomList` would silently break INV-007 with no test catching it. Adding the id as an explicit secondary comparator key (or a test that sorts on equal keys across a non-append write) would make it self-evident. Advisory only: no record clause is violated by the current commit.

The single advisory (RV-001) records that INV-007's `then by id` tie-break is implicit rather than explicit; it does not make any record fail, so the task is approved with the note going to trace.

choices:

- `BEH-011`/`BEH-012` are stated as HTTP-level `then` clauses ("the response is 400 with body …"), but this task owns only `src/core/**`; I judged them at the core seam (`parseTime` → `undefined`, `formatError("invalid_booking")` → 400 `{error:"invalid_booking"}`), which is the only layer T-001 can own, and treated "no booking is stored" as a downstream handler obligation rather than a missing core behaviour.
- `INV-001`'s negative case "a rejected creation => no id is consumed" has no store-level rejecting path; the store cannot exhibit a rejection, so I did not ask the test-writer for it and did not route it to `contract` — id non-consumption on validation failure is the room-creation handler's obligation (`addRoom` is only reached after validation).
- `INV-005` error-member set is asserted on `formatError` bodies rather than on HTTP responses; that is the highest layer this task exposes, and the handler layer composes solely from `formatError`, so the surface invariant is provable from it.
- `formatError("room_busy")` called without a conflict argument yields `{error:"room_busy"}` with no `conflictingBookingId`, which would not match `INV-005` if the surface ever emitted it. The `M-01` signature makes `conflict` optional by design and the surface only reaches `room_busy` through `earliestConflict`, so `INV-005`'s scope ("every response body of the surface") is not breached; I recorded it here rather than as a finding.
- `INV-006` is asserted through two independent `createStore()` instances rather than an actual process restart; since the invariant's whole content is "no state outside the process/in-memory container", an independent store is the layer-equivalent probe and a persisted or module-level store would fail it, so I accepted it as coverage.
- `INV-007`'s "by id" is read as ascending id order (numeric in practice, matching insertion order), since the record does not state a lexical form and no `negative_cases` entry distinguishes `b9`/`b10`; I did not ask for a tenth-booking ordering test as that would exceed the record's obligation.
- The `verifier.json` excerpt shows `changedFiles: ["src/core/index.ts"]` alongside a `tests/core/core.test.ts` that is new in this diff; I took `writeSetOk: true` (rule 3, mechanics from evidence) at face value rather than re-deriving whether the test file's addition is inside the `tests/core/**` write set.

## Findings

### RV-001 — advisory — target: implementer

- **spec_ids**: room-booking-api:CTR-009
- **evidence**: room-booking-api:CTR-009.schema.accepted — "a string whose calendar fields are valid, whose UTC designator is `Z`, and whose seconds part is `00`"; src/core/index.ts:88-91 — `Date.UTC(year, ...)` interprets a year of 0-99 as 1900+year, and the round-trip guard at :91 (`date.getUTCFullYear() !== year`) then returns `null`, so `parseTime("0050-01-01T00:00:00Z")` is refused even though its calendar fields are valid and its seconds part is `00`.
- **why advisory, not blocking**: the accepted text is a class claim, so strictly the class is not realised for four-digit years below `0100`. But CTR-009's `boundary_classes` (whole-minute UTC time, 30 seconds, `+02:00`, unparseable date), its `failure_scenarios`, and CTR-008's whole-minute start/end all sit in the current era; no record, task or design line names an ancient-year input, and the store sees booking times supplied by clients of a meeting-room API. The realised obligations are therefore provable and the divergence is confined to an input no record enumerates, so it is recorded for trace rather than as a rework trigger. If the maintainers want the class closed without argument, a year-gate before the `Date.UTC` call (or `new Date(0).setUTCFullYear(...)`) removes it.

No other finding. Specifically nothing blocking on: the missing HTTP-level assertions of CTR-007/CTR-008/CTR-010/INV-001/INV-003/POL-001 (status codes on real responses, `Content-Type`, the 409 body, listing order), because those are asserted by the module that owns the routes and lies outside this task's `writes`; the absent capacity and attendee validators, because the M-01 interface declares none and the constants are what the consumers read; and `statusOf` returning `undefined` for a value outside `ErrorCode`, because the type forbids that input and no record asks for a runtime guard.
